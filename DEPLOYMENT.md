# Deployment Guide — AppZex AgencyOS

Deploy to **Render (API)** + **Vercel (frontend)** + **MongoDB Atlas (database)**.

Both hosting providers have a free tier, which is enough to demo the assignment.

> The pieces must be deployed in this order: **database → API → frontend**. The frontend
> needs the API's public URL to build, and the API needs the frontend's origin for CORS.

---

## Why a Dockerfile for the API

This repository is an **npm workspace**, so dependencies are hoisted to the repo root:

```
$ cd backend && npm prefix
D:\AppZex          <-- resolves to the workspace root, not backend/
```

If a host simply ran `npm install` with its root directory set to `backend/`, npm would
detect the workspace and install the **entire Next.js frontend as well** — slow and wrong.

`backend/Dockerfile` removes that ambiguity: it copies only `backend/package.json`, so npm
treats the directory as a standalone project and the image contains the API and nothing
else.

This was validated locally: an isolated install of that manifest resolves 623 packages with
no workspace linking, and `backend/src` imports nothing outside itself.

## Step 1 — MongoDB Atlas (the database)

You cannot deploy on your laptop's MongoDB; a hosted database is required.

1. Sign up at <https://www.mongodb.com/atlas> (free tier, no card needed).
2. Create a free **M0** cluster — pick **Singapore** or **Mumbai** (closest to you).
3. **Database Access** → add a user:
   - Authentication: *Username & Password*
   - Username: e.g. `appzex`
   - Password: click **Autogenerate** and copy it somewhere safe
   - Privileges: *Read and write to any database*
4. **Network Access** → *Add IP Address* → `0.0.0.0/0` (allow anywhere). Render and Vercel
   deploy from shared IPs, so a single-IP allowlist will not work. This is acceptable for a
   demo because the API is unreachable without a valid JWT.
5. **Deployments** → *Database* → copy the **SRV connection string**:

```
mongodb+srv://appex:YOUR_PASSWORD@cluster0.xxxxx.mongodb.net/appzex_agencyos?retryWrites=true&w=majority
```

> Keep the generated password — you will need it for both Render and the seed step.

## Step 2 — Render (the API)

### 2a. Create the service

1. Sign up at <https://render.com> → **New → Blueprint**.
2. Connect the `AppZex` GitHub repository.
3. Render finds `render.yaml` at the repo root and shows the `appzex-agencyos-api` service.
4. Click **Apply**.

The blueprint sets the build to Docker (`backend/Dockerfile`) and health-check
`/api/health`. Env vars marked `sync: false` are intentionally not filled in by the file.

### 2b. Fill in the required secrets

Open **Environment** on the service and set:

| Key | Value |
| --- | --- |
| `MONGODB_URI` | The Atlas connection string from Step 1 |
| `CLIENT_URL` | Leave for now — added in Step 3 once you have the Vercel URL |
| `SUPER_ADMIN_EMAIL` | `admin@appzex-demo.com` (seed only) |
| `SUPER_ADMIN_PASSWORD` | A strong password (seed only) |
| `AI_API_KEY` | Optional. Leave unset to disable AI cleanly. |

`JWT_SECRET` is generated by Render automatically — never paste one in.

## Step 3 — Vercel (the frontend)

1. Sign up at <https://vercel.com> → **Add New → Project**.
2. Import the `AppZex` repository.
3. **Root Directory** — set this to **`frontend`**. Required for the monorepo.
4. Framework preset: **Next.js** (auto-detected). Leave the build command as default
   `next build`.
5. Deploy.

### 3a. Set the API URL (required)

Vercel bakes `NEXT_PUBLIC_API_URL` into the client bundle **at build time**, so it cannot be
a runtime value. Set it in **Settings → Environment Variables** for all environments:

| Key | Value |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | `https://appzex-agencyos-api.onrender.com/api` |
| `NEXT_PUBLIC_APP_URL` | your Vercel URL, e.g. `https://appzex.vercel.app` |

Note the trailing `/api` — the API base URL must include it.

After adding these, **redeploy** (Deployments → ⋮ → Redeploy). Adding an env var does not
rebuild an existing deployment automatically.

### 3b. Tell the API to allow the frontend's origin

CORS is an allow-list, so the API must be told about the Vercel domain. In
**Render → service → Environment**, set:

```
CLIENT_URL=https://appzex.vercel.app
```

Then redeploy the API. Without this the browser blocks every request with a CORS error, and
the login form will appear to hang.

## Step 4 — Seed the database

The seed wipes and repopulates collections, so run it **once**, after the API is live. Run it
from your machine using the same Atlas URI:

```powershell
cd D:\AppZex
$env:MONGODB_URI="mongodb+srv://appzex:YOUR_PASSWORD@cluster0.xxxxx.mongodb.net/appzex_agencyos?retryWrites=true&w=majority"
$env:NODE_ENV="production"
npm run seed
```

Expected output:

```
INFO seed.completed {"agencies":2,"users":8,"clients":4,"projects":6}
```

The Super Admin is created from `SUPER_ADMIN_EMAIL` / `SUPER_ADMIN_PASSWORD`.

## Step 5 — Verify the live deployment

Open your Vercel URL and check, in order:

1. `/` — landing page loads
2. `/login` — agency sign-in renders
3. Sign in as `agency-a-admin@appzex-demo.com` — workspace loads
4. `/admin/login` in an **incognito window** — sign in as Super Admin
5. Super Admin → Agencies → **Enter Support Mode** on Bluepeak (Agency B) — the banner
   appears and Agency B's data loads
6. `/client/login` in another incognito window — sign in as `agency-a-client@appzex-demo.com`
7. Workspace → Files → upload a document → download it

> If login spins forever, it is almost always **CORS**: `CLIENT_URL` on Render does not match
> your Vercel origin, or `NEXT_PUBLIC_API_URL` is missing the `/api` suffix.

## Custom domain (optional)

- **Frontend:** Vercel → Settings → Domains → add `appzex.yourdomain.com`.
- **API:** Render → Settings → Custom Domains. If you add one, update both variables so they
  still agree: Vercel `NEXT_PUBLIC_API_URL` → new API URL + `/api`, and Render `CLIENT_URL` →
  new frontend origin.

## Known deployment limitations

These are properties of the free tier and of local-disk storage, not defects in the app.

| Issue | Effect | Mitigation |
| --- | --- | --- |
| Render free tier sleeps after ~15 min idle | First request takes ~50s | Accept the cold start, or use a paid instance |
| Container filesystem is ephemeral | Uploaded files vanish on redeploy | Attach a Render **persistent disk**, point `STORAGE_DIR` at its mount path |
| `STORAGE_DIR` defaults to `/app/storage` inside the image | Works, but not durable | Use a disk mount for anything beyond a demo |
| Atlas `0.0.0.0/0` access | Database reachable from anywhere | The API still requires a valid JWT; tighten to static outbound IPs if available |

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| API deploy fails during build | Dockerfile build error | Read the Render build log; the failing step names the cause |
| Login page spins forever | CORS, or wrong `NEXT_PUBLIC_API_URL` | URL must end in `/api`; `CLIENT_URL` must match the Vercel origin exactly |
| 401 right after login | `JWT_SECRET` differs between instances | Render must generate **one** value; remove any manual override |
| Page loads but no data | API asleep | Wait ~50s and retry — free-tier cold start |
| `MONGODB_URI is required` | Env var not set | Set it in Render Environment and confirm the deploy is green |
| Frontend built before the var was set | Value is baked at build time | Add `NEXT_PUBLIC_API_URL`, then **redeploy** |
`https://appzex-agencyos-api.onrender.com`. Verify it:

```powershell
curl https://appzex-agencyos-api.onrender.com/api/health
# {"success":true,"data":{"status":"ok","service":"agencyos-api",...}}
```

> **Free tier note:** Render's free web services sleep after ~15 minutes idle, so the first
> request can take ~50 seconds while the instance wakes. That is expected, not a bug.
